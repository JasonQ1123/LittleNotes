# 小纸条开发流程

> 状态：v1.0（2026-10-20，维护者确认）。
> 定位：规定「需求怎么进、代码怎么改、什么时候算完成、怎么上线、出事怎么退」。
> 不替代：功能规则见 [功能规划](ROADMAP.md) 与各专题文档；部署命令见 [部署说明](../deploy/README.md)。
> 读法：先看第 0、3、12 节；落地按第 11 节执行。
> 说明：`AGENTS.md`、`docs/plan/`、`docs/lessons-learned.md` 已按本方案建立；后续文档按第 9 节归位。

## 0. 三分钟版

1. `main` 始终可发布；所有改动走短分支 + PR，即使只有一名维护者。
2. 需求只从 [待办总表](TODO.md) 进；复杂改动先写 `docs/plan/` 方案，关键规则确认后再写代码。
3. 提交保留现有中文类型前缀；非平凡改动写正文：为什么、改了什么、怎么验证、风险与回滚。
4. 合并门禁是 CI 全绿。数据库改动必须双库迁移 + PostgreSQL 浏览器回归；部署改动必须跑 `test:deploy` / `test:backup`。
5. 上线 = 打 tag + 发布清单 + 线上验收 + 回滚预案。回滚优先回应用，数据恢复只在维护窗口做。
6. 文档与代码同 PR 更新；踩过的坑写 `docs/lessons-learned.md`。
7. AI 必须先读 `AGENTS.md`；不得擅自部署、改生产数据、强推 `main` 或合并 PR。

## 1. 为什么现在定流程

项目已有真实用户和生产数据，但开发过程主要靠记忆和长文档维持：直接提交 `main`、没有版本 tag、发布步骤散落在部署说明和规划文档里。单人开发时这些不是大问题，一旦出现「隔了一个月再改」「AI 接手」「线上要回滚」，成本和风险会明显放大。

### 1.1 目标

- 任何一个线上版本，都能定位到确定的提交、部署包和发布时间。
- 任何一次改动，都能回答：为什么改、改了什么、验证了什么、怎么退。
- 新协作者或 AI 在十分钟内能找到入口、命令和红线。
- 踩过的坑只踩一次，非显而易见的结论不留在聊天记录里。

### 1.2 非目标

- 不搭 staging 多环境，不做自动 CD。当前是单台 2 GB 服务器 + 手动部署，自动化收益不足以覆盖维护成本。
- 不追求测试覆盖率数字，不为了流程增加审批层级。
- 不要求每个小改动都写设计文档。
- 不照搬大型团队的分支模型、发布火车和值班制度。

### 1.3 原则

- **能自动检查的，不靠自觉。** 格式、构建、测试、迁移同步尽量交给 CI。
- **一个事实只写一处。** 其它地方用链接，不复制。
- **小步、可独立回滚。** 一个 PR 一个主题，一个发布一组相关改动。
- **生产变更必须有退路。** 先备份，再迁移；先能回应用，再谈恢复数据。
- **规则少，但硬的要硬。** 数据、隐私、生产操作不靠「下次注意」。

## 2. 现状与参考项目对照

### 2.1 接手时的风险（2026-10-19 盘点）

| 现状                                        | 风险                                                                |
| ------------------------------------------- | ------------------------------------------------------------------- |
| 提交直接落在 `main`，没有 PR                | 没有独立评审点；CI 在推送后才跑；回滚粒度只能是整条历史             |
| 没有 tag / GitHub Release                   | 上线版本靠记忆和 ROADMAP 文字；规划里已出现「未提供具体生产版本号」 |
| 工作区长期有未提交改动                      | 打包脚本要求干净工作区；容易漏提交或把无关改动带进发布              |
| Prettier 已安装，但 CI 不检查               | 格式靠手动，diff 噪音多；历史上「格式检查通过」是人工结论           |
| 没有 ESLint                                 | 类型之外的问题靠人眼，已在 TODO 记为 S6                             |
| 文档分散在 README / ROADMAP / TODO / deploy | 同一事实多处维护，容易过期；AI 没有统一入口                         |
| 发布步骤写在长文档里                        | 依赖记忆，漏备份、漏验收的风险高                                    |
| 没有踩坑记录                                | 非显而易见的结论只留在对话或提交里，下次重新踩                      |

## 3. 端到端流程

```text
需求入池 → 方案确认 → 分支开发 → 本地自检 → PR/CI → 合并 → 打包 → 上线 → 验收/记录 → 复盘
```

| 阶段     | 输入                 | 产出                                | 门禁                             | 负责人      |
| -------- | -------------------- | ----------------------------------- | -------------------------------- | ----------- |
| 需求入池 | 用户反馈、自查、事故 | TODO 条目（编号、优先级、验收标准） | 有可验证的验收标准               | 维护者      |
| 方案确认 | TODO 条目            | `docs/plan/` 方案或 TODO 小节       | 关键规则由维护者确认             | 维护者 + AI |
| 分支开发 | 已确认方案           | 分支 + 小提交                       | 本地构建/相关测试通过            | AI / 维护者 |
| 评审     | PR                   | PR 描述、自审结论                   | CI 全绿、无未提交改动            | 维护者      |
| 合并     | 通过评审的 PR        | squash 到 `main`                    | 线性历史、分支删除               | 维护者      |
| 发布     | `main` + tag 计划    | 部署包、发布记录、tag               | 发布清单全部通过                 | 维护者      |
| 验收     | 线上服务             | 验收记录                            | 健康检查、登录、核心流程、移动端 | 维护者      |
| 复盘     | 事故、返工、绕路     | `docs/lessons-learned.md` 条目      | 非显而易见的问题 24 小时内记录   | 维护者 + AI |

## 4. 需求与方案

### 4.1 需求入口

- [待办总表](TODO.md) 是排期的唯一入口，沿用现有约定。
- 新需求先加编号（`S` 工程/安全、`U` 界面、`C` 合规，接现有编号），写清：现状、做法、验收、优先级。
- 确认要做后，在 [功能规划](ROADMAP.md) 增加条目或链接；TODO 条目保留到上线完成。
- 一句话需求也要有验收标准。没有验收标准的事项不进入开发。
- 聊天里定下的规则，当天回写到文档；只存在于对话里的决定视为未确认。

### 4.2 什么时候必须写方案

满足任一条件，先在 `docs/plan/<slug>.md` 写方案：

- 改数据模型、迁移或清理规则；
- 改权限、隐私边界或共享范围；
- 改部署、备份、回滚方式；
- 引入外部服务、新依赖或持续费用；
- 预计超过 2 人日，或横跨 3 个以上核心文件；
- 包含不可逆操作（删除、注销、批量清理）。

其余改动：TODO 条目 + PR 描述即可，不为了流程写空文档。

### 4.3 方案文档要求

模板见附录 B。硬要求只有三条：

- 「待确认」必须单独列出，不能把建议写成已确认规则。
- 写清上线步骤和回滚方式；涉及迁移的，写清旧数据怎么办。
- 方案状态随进展更新：草稿 → 已确认 → 实施中 → 已交付 / 已放弃。

### 4.4 范围与缺陷

- 一个 PR 一个主题；顺手发现的问题记入 TODO，不夹带进当前 PR。
- 需求变更先改文档再改代码；紧急情况可先处理，24 小时内补记录。
- 缺陷分级沿用 TODO 的 P0/P1/P2：P0 立即修，P1 进入下个发布，P2 排期。

## 5. 分支、提交与 PR

### 5.1 分支

采用主干开发 + 短分支。分支从 `main` 拉出，合并前 rebase 到最新 `main`。

| 前缀        | 用途                 | 示例                     |
| ----------- | -------------------- | ------------------------ |
| `feat/`     | 新功能               | `feat/account-deletion`  |
| `fix/`      | 缺陷修复             | `fix/avatar-upload-413`  |
| `docs/`     | 文档                 | `docs/dev-process`       |
| `refactor/` | 不改变行为的重构     | `refactor/records-query` |
| `perf/`     | 性能                 | `perf/statistics-load`   |
| `test/`     | 测试                 | `test/space-lifecycle`   |
| `deploy/`   | 部署、CI、脚本       | `deploy/backup-oss`      |
| `hotfix/`   | 线上紧急修复         | `hotfix/login-500`       |
| `chore/`    | 依赖、配置、工程杂项 | `chore/dependabot`       |

- 分支名用小写英文和连字符，不用中文，避免工具兼容问题。
- 分支存活不超过 3 天；做不完就拆成可独立合并的小 PR，不长期挂一个大分支。
- 合并后删除远端和本地分支。

### 5.2 提交信息

保留现有中文类型前缀，格式：

```text
类型：一句话概述

为什么：
改了什么：
怎么验证：
风险与回滚：
Refs: S2
```

类型固定为：`功能`、`修复`、`文档`、`测试`、`部署`、`重构`、`性能`、`样式`、`工程`、`安全`、`CI`。

规则：

- 标题不超过 50 个字符，不加句号；同一提交只做一件事。
- `功能`、`修复`、`部署`、`安全` 必须写正文；`文档`、`测试`、`样式` 可只写标题。
- 格式化与行为改动分开提交，避免 review 时被空白淹没。
- 不提交 `.env`、`*.db`、`uploads/`、`test-results/`、`playwright-report/`、`.cache/`、密钥和真实用户数据。
- 提交前看一遍 `git diff --staged`，确认没有调试代码、日志和无关文件。
- 不使用 `update`、`fix bug`、`修改` 这类无信息标题。

### 5.3 Pull Request

即使单人开发也建议开 PR：它提供一次完整的 diff 视图、一次 CI 运行和一份可检索的变更说明。

- 标题与 squash 后的提交标题一致；正文用附录 A 的模板。
- 必须关联 TODO/ROADMAP 编号，写清验证命令和结果。
- 作者先自审：通读 diff、检查密钥/调试代码、检查双库迁移、检查文档是否同步。
- 规模控制在 400 行以内（不含 lockfile 和迁移 SQL）；超过就拆。
- 未完成的改动开 Draft PR，CI 照常运行。
- 合并方式统一 squash，保持 `main` 线性；合并后删除分支。
- CI 是底线，不替代本地关键验证；没跑过的门禁不要写「已通过」。

### 5.4 `main` 保护

已确认使用 GitHub 分支保护 / Ruleset：

- 合并前必须经过 PR；
- 必须通过 CI 的 `test` 和 `containers` 检查；
- 禁止 force push 和删除分支；
- 要求线性历史；
- **不要求人工 approval**——单人项目会把自己锁死；有第二位维护者后再加。

仓库已转为公开，GitHub Free 的 ruleset 会直接强制执行。维护者需要确认：目标分支包含 `main`、enforcement 为 Active、required checks 已包含 `test` 和 `containers`。规则集保留即可，转公开后自动生效。

### 5.5 紧急修复

- 从 `main` 拉 `hotfix/<slug>`，只改导致故障的最小范围。
- 仍然走 PR 和 CI；与部署无关时可只跑 `test` 任务，但要在 PR 里说明跳过了什么。
- 合并后打补丁 tag、按发布清单上线，24 小时内补 lessons 条目。
- GitHub 不可用等极端情况：允许本地修复并部署，但必须在恢复后 24 小时内补推分支、PR 和记录。

### 5.6 禁止事项

- 禁止 force push `main` 或改写已发布历史。
- 禁止绕过 CI 合并。
- 禁止把密钥、生产数据、用户隐私写进仓库、PR、Issue 或截图。
- 禁止在脏工作区打包或部署（`package-deploy` 已强制检查）。
- 禁止把多个不相关功能捆进同一次发布。
- 禁止在共享分支上 `git reset --hard`。

## 6. 工程约定

### 6.1 目录职责

| 路径                       | 职责                                        |
| -------------------------- | ------------------------------------------- |
| `apps/api/src/`            | NestJS 控制器、服务、DTO、权限与 AI 契约    |
| `apps/api/prisma/`         | SQLite 模型与迁移；`postgresql/` 为生成副本 |
| `apps/api/test/`           | API 集成测试                                |
| `apps/web/src/views/`      | 页面                                        |
| `apps/web/src/components/` | 可复用组件                                  |
| `apps/web/src/api.ts`      | 请求、错误和操作提示的统一入口              |
| `tests/`                   | Playwright 双人流程与专项回归               |
| `scripts/`                 | 环境初始化、测试、打包等独立脚本            |
| `deploy/`                  | Compose、Caddy、备份、部署与恢复脚本        |
| `docs/`                    | 规划、方案、流程、专题说明                  |
| `.github/`                 | CI 与仓库模板                               |

### 6.2 API

- 控制器保持薄；业务规则和事务放在服务层。
- 所有输入走 DTO + `class-validator`；不使用 `any` 接住请求体。
- 空间与权限判断统一走 `space-access.ts`，不信任客户端传入的空间/成员 ID。
- 多表写入放在 `Database.atomic` 内；记录、视角、约定的修改保留版本校验。
- 错误返回稳定的 HTTP 状态和业务码；响应不含堆栈、密码、Cookie、邮箱等敏感信息。
- 新接口同步 Swagger 注解；鉴权、限流、来源校验沿用现有模式。
- 不新增 `console.*` 作为日志方案；结构化日志按 TODO S4 统一做。
- AI 接口先做权限检查；关闭时不得产生供应商请求。

### 6.3 数据与迁移

- 模型源文件是 `apps/api/prisma/schema.prisma`（SQLite）；改完执行 `pnpm db:postgres:sync`，提交生成的 `postgresql/schema.prisma`。
- 每次模型变更写两份迁移（SQLite 与 PostgreSQL），时间戳和名称保持一致；已应用的迁移不再修改。
- 迁移命名：`YYYYMMDDHHMMSS_snake_case`，名称描述结果而不是过程。
- 本地用 `pnpm --filter @paper/api db:migrate`，PostgreSQL 用 `pnpm --filter @paper/api db:postgres:migrate`；生产只允许 `prisma migrate deploy`，禁止 `migrate dev`、`db push`、`migrate reset`。
- 破坏性变更采用 expand/contract：先加新字段 → 回填/双写 → 切换读 → 下个版本再删旧字段。
- 生产迁移前必须有成套备份；部署脚本会自动备份，失败即中止。
- 数据修复写成一次性脚本，事务内执行并核对行数；不在生产库手工改数据。
- 涉及模型或权限的改动，发布前跑 `pnpm test:postgres --e2e`，使用 `ln_test_` 独立 schema。

### 6.4 前端

- 所有 HTTP 请求走 `api.ts`，统一处理错误和提示；不在组件里裸写 `fetch`。
- 会话与空间状态放 `store.ts`，页面不各自维护登录态。
- 新页面放 `views/`，可复用 UI 放 `components/`；样式优先复用现有类和变量，token 化按 UI_TODO 第二批推进。
- 每个页面至少覆盖：加载、空状态、错误、禁用/提交中、键盘操作、390px 布局。
- 新页面需通过 axe WCAG A/AA 检查，无横向溢出。
- 不新增硬编码色值；主题收敛按 UI_TODO 第二批执行，避免继续扩大两套样式。
- 组件内样式优先作用域化，不往全局 CSS 追加一次性规则。

### 6.5 代码风格

- Prettier 是格式的唯一标准；补齐 `format` / `format:check` 脚本后，提交前跑 `pnpm format`，CI 跑 `pnpm format:check`。
- TypeScript 已开启 `strict`；避免 `any` 和 `@ts-ignore`，确需使用时写明原因。
- 命名跟随相邻文件：变量/函数 camelCase，类型/组件 PascalCase，文件名沿用现有习惯。
- 注释解释「为什么」，不复述代码；行为变化时同步更新注释。
- 删除死代码和注释掉的旧实现，历史交给 git。
- 重复三次以上再抽象；不为一次性逻辑提前造框架。

### 6.6 安全与隐私

- 密钥只放 `.env` 或服务器环境，绝不进仓库、PR、Issue、日志。
- 生产 Cookie 使用 `Secure` + `HttpOnly`；`WEB_ORIGIN` 来源校验不得放宽。
- 上传校验类型、大小并重新编码；文件名随机；读取时校验登录与空间权限。
- 日志不记录密码、令牌、Cookie、完整邮箱、原始 IP；需要统计时存哈希。
- 邮件生产必须真实 SMTP，模拟投递只用于本地和 CI；`EMAIL_SMTP_VERIFIED` 守卫不得绕过。
- 新增依赖先确认维护状态和许可证；依赖更新按 TODO S7 接入自动化。
- 共享范围以服务端判断为准：草稿、未发布视角、已关闭空间内容不得出现在列表、统计、导出或 AI 投影中。

### 6.7 用户可见文案

- 只描述当前规则、条件、结果和操作；不写版本改动、迁移说明、设计理由或开发自述。
- 术语统一：空间、纸条、视角、约定、回访、归档；不混用「帖子」「事件」等内部叫法。
- 错误提示说清「发生了什么 + 接下来怎么做」，不只给错误码。
- 时间统一按北京时间展示；日期格式保持一致。
- 涉及不可逆操作时，明确说明后果和确认方式，不用模糊措辞。

## 7. 质量门禁与完成定义

### 7.1 四道门

| 门禁      | 时机       | 内容                                                                  |
| --------- | ---------- | --------------------------------------------------------------------- |
| G0 本地   | 提交前     | 格式化、构建、相关测试；涉及迁移时双库验证                            |
| G1 PR CI  | 开 PR 后   | `format:check`、`setup`、`build`、`test`、`test:deploy`、PG e2e、容器 |
| G2 发布前 | 打包前     | 全量测试、迁移检查、备份确认、回滚目标确认、部署包 SHA256             |
| G3 上线后 | 部署完成后 | 健康检查、登录、核心流程、移动端、日志；至少观察 1 小时               |

测试取舍：优先覆盖权限边界、状态机、并发和迁移；E2E 只保主流程与移动端，不为视觉细节写脆弱断言；能用 API 测试覆盖的，不堆到浏览器层。修 bug 先补一个能复现的失败用例，再修。

### 7.2 改动类型矩阵

| 改动类型        | 本地至少跑                             | 发布前额外                       |
| --------------- | -------------------------------------- | -------------------------------- |
| 文档 / 文案     | `pnpm format:check`                    | 检查链接和事实                   |
| 前端 UI         | `pnpm build`、相关 Playwright spec     | 390px 手测/截图                  |
| API / 业务规则  | `pnpm build && pnpm test`              | `pnpm test:e2e`                  |
| 数据模型 / 迁移 | 双库迁移、`pnpm test:postgres --e2e`   | 备份校验、恢复演练（结构性变更） |
| 部署 / 脚本     | `pnpm test:deploy`、`pnpm test:backup` | 容器冒烟、备份恢复               |
| 依赖升级        | `pnpm build && pnpm test`              | 全量回归、观察 24 小时           |

- [ ] 用户可见文案符合 6.7。
- [ ] 相关文档与部署说明已同步。
- [ ] 涉及发布的，写清回滚目标和数据影响。
- [ ] 工作区干净，提交信息完整，分支已合并删除。

## 8. 发布与回滚

### 8.1 版本与 tag

- 版本唯一来源是 git tag，格式 `vYYYY.MM.DD`；同一天多次发布用 `vYYYY.MM.DD.2`。
- 使用 annotated tag，说明写清：发布范围、提交、部署包 SHA256、回滚目标。
- **tag 只打在已经验收的提交上**，代表「这个版本确实上过生产」，不是「准备发布」。
- 不在 README、`package.json` 或代码里维护第二份版本号。
- 上一个 tag 就是默认回滚目标，必须保留对应部署包。

示例（取自 2026-09-22 上线记录）：

```bash
git tag -a v2026.09.22 -m "上线：空间彻底删除与域名切换
commit: f72767d
sha256: 879a2da..."
git push origin v2026.09.22
```

GitHub Release 可用 `gh release create v2026.09.22 --generate-notes` 生成变更摘要（也可在网页创建）；不单独维护 CHANGELOG。

### 8.2 发布节奏

- 按需发布，一次发布只包含一组相关改动。
- 选择低使用时段，并留出至少 1 小时观察窗口；无法观察时不发布。
- 2 GB 服务器构建期间 `web` 和 `api` 会停止，存在维护中断，提前有心理预期。
- 连续大改分多次发布，避免一次部署同时引入多个不确定因素。

### 8.3 发布前

- [ ] 本次范围已在 TODO/ROADMAP 写清，没有夹带未验证改动。
- [ ] 目标提交在 `main` 上，CI 全绿，工作区干净。
- [ ] 本地 `pnpm build && pnpm test` 通过。
- [ ] UI/流程改动跑过 `pnpm test:e2e`；API/数据改动跑过 `pnpm test:postgres --e2e`。
- [ ] 迁移两份齐全且已同步；生产迁移前有备份。
- [ ] 上一个 tag 和部署包可用，回滚方式明确。
- [ ] 部署包已生成并记录 SHA256。

```powershell
git switch main
git pull --ff-only
git status --short          # 必须为空
pnpm install --frozen-lockfile
pnpm build
pnpm test
pnpm test:e2e               # UI/流程改动时
pnpm package:deploy         # 产出 .cache/releases/littlenotes-deploy.tar.gz 与 .sha256
```

### 8.4 上线

按 [部署说明](../deploy/README.md) 的更新流程上传源码包，然后在服务器执行：

```bash
cd /opt/littlenotes
sudo bash deploy/deploy.sh
```

脚本顺序是：检查 SMTP 验收标记 → 成套备份 → 停止 `web`/`api` → 构建 → 数据库迁移 → 启动 → 内部健康检查（未开放公网时）或提示走 HTTPS 验收（已开放时）。任一步失败会中止，不会继续覆盖。

- 不执行 `docker compose down -v`，它会删除数据库和证书卷。
- 不在生产手工改 schema 或跳过迁移。
- 保留上一版源码包和镜像，作为回滚材料。

### 8.5 上线后验收

至少完成：

1. `https://web.littlenotes.cn/api/health` 返回正常，证书有效。
2. 登录、首页、纸条列表与详情可打开。
3. 本次改动对应的主流程走一遍（双人流程、头像、邮箱、空间等按范围选择）。
4. 390px 宽度下无横向溢出，关键按钮可操作。
5. 服务器日志无持续 5xx；浏览器控制台无异常。
6. 至少观察 1 小时；涉及邮件、定时清理、备份的，确认对应任务有成功记录。

### 8.6 回滚决策

原则：**先回应用，再考虑恢复数据；数据恢复只在维护窗口做。**

| 症状                       | 判断               | 动作                                                   | 数据影响               |
| -------------------------- | ------------------ | ------------------------------------------------------ | ---------------------- |
| 新版本 5xx、白屏、接口报错 | 数据库正常         | 用上一个 tag 重新打包部署，保留当前 schema             | 通常无数据损失         |
| 迁移执行失败               | 应用尚未切到新版本 | 重新部署上一版应用；修正迁移后重试，不手工改表         | 无新增写入             |
| 数据被错误删除/覆盖        | 确认影响范围       | 停写 → 取最近验证过的备份 + 头像归档恢复 → 核对 → 重开 | 会丢失备份点之后的数据 |
| 邮件发送失败               | 业务主流程不受影响 | 回退 SMTP 配置；修复后再部署；不要关闭投递校验绕过问题 | 无数据影响             |
| 性能骤降/内存不足          | 新版本引入         | 回滚应用；排查构建或查询变化                           | 无数据影响             |

回滚后必须：记录时间线、影响范围、恢复方式；在 `docs/lessons-learned.md` 补条目；确认监控/日志恢复正常。

### 8.7 发布记录

每次上线在 [功能规划](ROADMAP.md) 第 9 节追加一条，模板见附录 C；同时创建 GitHub Release。README 只更新用户可见的「当前上线状态」，不复制发布细节。

## 9. 文档与知识

### 9.1 文档地图

| 文件                      | 负责内容                                 | 更新时机                 | 不该放什么             |
| ------------------------- | ---------------------------------------- | ------------------------ | ---------------------- |
| `README.md`               | 项目是什么、当前上线状态、功能清单、运行 | 功能上线、入口或配置变化 | 逐次发布记录、详细排期 |
| `docs/DEVELOPMENT.md`     | 开发流程（本文）                         | 流程变化                 | 具体功能规则           |
| `docs/ROADMAP.md`         | 已确认需求、方案要点、交付记录           | 需求确认、上线           | 未确认的猜测           |
| `docs/TODO.md`            | 未做事项、优先级、验收                   | 新增、完成、调整优先级   | 已完成的细节           |
| `docs/UI_TODO.md`         | 界面问题与批次                           | UI 批次推进              | 工程/运维事项          |
| `docs/plan/<slug>.md`     | 单个复杂改动的设计与决策                 | 方案确认、实施、交付     | 日常流水账             |
| `docs/lessons-learned.md` | 踩坑、根因、做法                         | 非显而易见问题解决后     | 通用编程知识           |
| `deploy/README.md`        | 安装、升级、备份、恢复操作               | 部署方式变化             | 产品需求               |
| `AGENTS.md`               | AI/协作者入口、命令、红线                | 命令、目录、约束变化     | 与本文重复的长篇规则   |
| GitHub tag / Release      | 版本与变更摘要                           | 每次上线                 | 内部讨论               |

### 9.2 维护规则

- 同一事实只保留一个权威位置，其它地方链接过去。
- 状态只写一处：TODO 表示「没做」，ROADMAP 表示「已交付」，README 表示「当前线上」。
- 文档跟代码在同一个 PR 更新；不积压「下次一起改」。
- 大幅更新时在文首写更新日期；发现过期内容立即修正或删除，不留自相矛盾的两段。
- 专题文档用 `docs/<TOPIC>.md`；一次性方案用 `docs/plan/<slug>.md`，交付后保留并标记状态。
- README 不再继续膨胀：新增实现细节写专题文档，README 只留入口和结论。

### 9.3 `lessons-learned.md`

什么时候写：非显而易见的失败、绕路、根因、外部约束、线上事故、重复犯的错。

格式见附录 D。要求：

- 一条经验一个条目，标题直接写结论。
- 写清触发场景、症状、根因、做法、如何预防。
- 链接相关提交/PR/文档，不复制大段代码。
- 同类问题第二次出现时必须补条目；一次性、无复用价值的流水账不写。

### 9.4 方案文档的生命周期

草稿 → 已确认 → 实施中 → 已交付 / 已放弃。交付后保留原文，更新状态和实际差异；放弃时写清原因，不删除历史。

## 10. AI 协作

### 10.1 `AGENTS.md`

根目录的 `AGENTS.md` 是人和 AI 的共同入口，控制在 120 行以内。它包含：

- 一句话项目说明与技术栈；
- 常用命令（安装、开发、构建、测试、打包）；
- 目录地图与「改什么去哪里」；
- 硬约束：双库迁移、权限边界、生产操作、禁止事项；
- 完成定义与文档索引；
- 指向本文和 `docs/lessons-learned.md`。

不复制本文的长篇流程；`AGENTS.md` 只做索引和红线。

### 10.2 授权边界

| 动作                                      | 规则                                 |
| ----------------------------------------- | ------------------------------------ |
| 读代码/文档、跑测试、改代码、写文档       | 可直接做                             |
| 新增依赖、改 CI、改部署脚本、改数据模型   | 先说明方案，维护者确认后再做         |
| 创建分支、提交、推送、开 PR               | 可做；合并必须由维护者完成           |
| 部署、重启生产、改生产数据、改 `.env`     | 仅在维护者明确指示下进行，并逐步确认 |
| force push、删除分支/数据、`reset --hard` | 禁止                                 |
| 读取或输出密钥、Cookie、用户隐私          | 禁止                                 |

### 10.3 工作方式

- 开始前先读 `AGENTS.md`、相关专题文档和 TODO 条目；不清楚的产品规则先问，不自行发明。
- 多文件改动先给出简短计划，再动手；一个任务一个分支。
- 小步提交；提交前跑对应门禁，并在回复中给出实际命令和结果。
- 没有运行过的检查不写成「通过」；失败就如实报告，不绕过。
- 结束时保持工作区干净；未完成的部分说明原因和下一步。
- 交付时同步更新 TODO/ROADMAP、方案文档和 lessons（如适用）。

### 10.4 知识沉淀

- 决定写进文档，不留在聊天里。
- 非显而易见的修复，24 小时内补 lessons 条目。
- 不把密钥、生产数据、用户隐私写进任何知识文件。
- 不为一次性问题新建文档；先判断能否并入现有文档。

## 11. 落地计划

### 11.1 第一阶段：评审后当天（约 1 小时）

1. 收口当前工作区：把 README、主题、统计页等未提交改动按主题归类，拆成少量 PR 或明确暂存，不直接堆在 `main`。
2. 把本文定稿为 `docs/DEVELOPMENT.md`，新增 `AGENTS.md`、`.github/pull_request_template.md`。
3. 根 `package.json` 增加 `format` / `format:check`；先格式化现有文件，再在 CI 增加检查。
4. 为当前生产提交补 tag（以维护者确认的实际部署提交为准）。
5. 开启 `main` 保护 / Ruleset，确认已生效。

**验收：** `pnpm format:check` 通过（未提交的草稿先 `pnpm format` 收口）；下一次改动走分支 + PR；生产提交有 tag。

### 11.2 第二阶段：两周内

1. 完整走一次「分支 → PR → CI → 合并 → 打包 → 上线 → 验收 → 记录」。
2. 增加 Issue 模板（缺陷、功能建议），减少来回追问。
3. 写第一篇 `docs/lessons-learned.md`。
4. 用发布记录模板补一次历史版本记录。

**验收：** 完成一个完整发布闭环；回滚目标明确；发布记录可追溯。

### 11.3 第三阶段：按 TODO 推进

1. TODO S6：ESLint + CI 阻断。
2. TODO S7：Dependabot + 依赖审计。
3. CI 并发、超时、路径过滤等成本优化。
4. 可选：把重复度高的流程固化为 `.agents/skills/`（发布、迁移），没有重复痛点就不做。
5. 逐步收敛 README，把实现细节迁到专题文档。

### 11.4 流程健康度

不追求数字指标，只看五件事：

- 每次上线都有 tag 和发布记录；
- 没有从脏工作区打出的包；
- 数据库改动都带双库迁移和 PostgreSQL 回归；
- 事故和非显而易见的问题都有 lessons；
- `main` 长期保持 CI 绿色。
