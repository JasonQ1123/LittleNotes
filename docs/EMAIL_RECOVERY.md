# 邮箱验证与找回密码

## 使用规则

继续使用用户名和密码登录。新用户注册时验证邮箱；旧用户用原密码登录后进入独立绑定页，验证当前密码与邮箱验证码后继续访问原页面。未验证邮箱时，空间、纸条、统计和个人资料等业务接口返回 `403 EMAIL_BINDING_REQUIRED`。旧密码、昵称、头像、空间和纸条均保留。

一个邮箱只对应一个账号；去掉首尾空白并转为小写，不合并邮箱别名。本人资料只返回脱敏邮箱，成员及纸条接口不返回邮箱。尚未绑定且已经忘记密码的旧账号暂不支持自助恢复。

- 注册：用户名、昵称、密码、邮箱 → 获取验证码 → 验证后创建账号。
- 首次绑定：原密码登录 → 当前密码、邮箱、验证码 → 轮换当前会话，撤销其他会话。
- 找回：登录页“忘记密码” → 已验证邮箱、验证码、新密码及确认 → 撤销全部会话，回到登录页。
- 更换：我们的空间 → 账号安全 → 更换邮箱 → 当前密码及新邮箱验证码 → 成功后退出所有设备。成功前旧邮箱仍有效，成功后旧邮箱不能再找回此账号。

注册、修改和重置的新密码均为 8–32 位，必须同时包含英文字母和数字，可额外包含符号。登录与当前密码校验继续兼容旧 8–128 位规则。不提供短信、密保问题、恢复码、邮箱免密登录或管理员重置页面。

## 本地验收

2026-09-06 用户确认“本地收发功能测试通过”和“忘记密码测试通过”，本地模拟验证码收发及忘记密码流程已验收；同日也确认修改密码测试通过。阿里云服务器的真实 SMTP 投递仍待验证，尚未上线生产。

执行 `pnpm run setup` 后启动 `pnpm dev`。默认 `EMAIL_DELIVERY=mock`，不会发送真实邮件。申请验证码后打开表单的“本地模拟收件箱”，稍等片刻后刷新，复制对应邮箱与用途的验证码。收件箱地址为 [http://localhost:5173/dev-mail](http://localhost:5173/dev-mail)。

模拟收件箱只保存在服务进程内存，最多保留 200 封未过期邮件，重启后清空；仅非生产 mock 模式及回环地址请求可读取 `/api/dev/mail`。这是开发测试专用入口，普通验证码接口不返回验证码。不要将开发服务反向代理到公网。生产环境拒绝 mock 模式，收件箱接口返回 404。

初始化脚本为本地 `.env` 补充独立随机 `EMAIL_HMAC_SECRET`，保留已有配置。服务重启后未发送任务继续处理；如果已发送邮件仅存在模拟收件箱而进程重启，应在冷却后重新申请。CI 使用独立数据库和模拟收件箱，E2E 调低冷却、提高配额，不改变生产默认值。

建议验收：旧账号打开原纸条链接并登录，确认先绑定再回原页；用两个浏览器登录同一账号，分别检查首次绑定、换绑、重置后的会话结果；重置后旧密码失效；昵称头像和共同空间仍正常。

## 配置与发送策略

正式发件使用 Nodemailer，固定 `smtp.163.com:465`、TLS（校验证书，最低 TLS 1.2），显示名“小纸条”。在专用 163 邮箱开通 SMTP 后，配置 **SMTP 授权码**，不要填写邮箱登录密码。

| 环境变量                 | 默认或要求                                                             |
| ------------------------ | ---------------------------------------------------------------------- |
| `EMAIL_DELIVERY`         | 本地 `mock`，生产必须 `smtp`                                           |
| `SMTP_USER`              | 专用 `@163.com` 发件邮箱                                               |
| `SMTP_AUTH_CODE`         | SMTP 授权码，保存在服务器环境                                          |
| `EMAIL_HMAC_SECRET`      | 独立随机密钥，SMTP 模式至少 64 位十六进制；`openssl rand -hex 32` 生成 |
| `EMAIL_COOLDOWN_SECONDS` | 同邮箱跨用途 60 秒                                                     |
| `EMAIL_LIMIT_EMAIL_HOUR` | 同邮箱每小时 5 次                                                      |
| `EMAIL_LIMIT_EMAIL_DAY`  | 同邮箱每天 10 次                                                       |
| `EMAIL_LIMIT_IP_HOUR`    | 同 IP 每小时 20 次                                                     |
| `EMAIL_LIMIT_GLOBAL_DAY` | 全站每天 200 次                                                        |
| `EMAIL_SMTP_VERIFIED`    | 部署脚本的人工收信验收标记；确认实际投递后在 `deploy/.env` 设置 `1`    |

SMTP 凭证和 HMAC 密钥只放 `.env` 或服务器环境，不提交 Git，不传前端，不在日志中输出。所有 API 实例必须共用同一 HMAC 密钥；更换密钥会使尚未使用的验证码失效。数据库备份以外还需安全保管配置文件。

限额使用从窗口首个申请开始计算的滚动固定窗口（1 小时或 24 小时），由数据库保存，支持重启与多实例；IP 和邮箱限流键使用 HMAC。超限返回 429 和 `retryAfter`。绑定/换绑的当前密码验证还受账号安全限额约束：15 分钟每账号 5 次、每 IP 40 次，申请和提交都会计数。

验证码为随机 6 位数字，自申请起 10 分钟有效，同邮箱同用途只接受最新申请；注册、首次绑定、换绑和重置分别限定用途。验证码只能使用一次，累计输错 5 次后永久失效，正确使用前的格式错误不会消费验证码。

申请请求在数据库中保存挑战及发送任务，不等待 SMTP。后台领取任务时才生成明文验证码，将 HMAC 摘要写入挑战，然后发送；数据库不保存可恢复的明文验证码、邮件正文或授权码。已过期或已撤销任务跳过；SMTP 失败或结果不确定时标为 `uncertain`，撤销挑战，**不自动重发**。超过两分钟仍处于发送中的任务视为中断，同样不重发。用户可在冷却后重新申请。过期挑战及任务在到期 24 小时后自动清理。

找回申请对存在与不存在的邮箱都创建同形态挑战、返回相同提示“如该邮箱已绑定账号，将收到验证码”；是否投递在后台判断。不存在的邮箱不会收到邮件。申请注册/绑定到已占用邮箱时同样不发验证码，完成接口始终检查唯一性。

## 接口与数据一致性

| 接口                                 | 请求                                                     |
| ------------------------------------ | -------------------------------------------------------- |
| `POST /api/auth/register/code`       | `email`                                                  |
| `POST /api/auth/register`            | `username, nickname, password, email, challengeId, code` |
| `POST /api/auth/email/code`          | 登录态、`currentPassword, email`                         |
| `PUT /api/auth/email`                | 登录态、`currentPassword, email, challengeId, code`      |
| `POST /api/auth/password/reset/code` | `email`                                                  |
| `POST /api/auth/password/reset`      | `email, challengeId, code, newPassword, confirmPassword` |

申请成功返回 `challengeId, retryAfter, message`。首次绑定返回 `{ ok: true, requiresLogin: false }` 并写入新的 Cookie；换绑返回 `requiresLogin: true` 并清 Cookie。重置返回 `{ ok: true }` 并清 Cookie。本人登录状态额外返回 `requiresEmailBinding` 和 `maskedEmail`，不返回内部认证版本。

`User` 新增可空唯一邮箱、验证时间、`authVersion`；新增 `EmailChallenge`、`EmailJob`、`EmailLimit`。SQLite 与 PostgreSQL 均有 `20260906020000_email_recovery` 增量迁移，只加列与表，旧邮箱保持空，不重写旧哈希。

验证码消费、邮箱/密码更新、认证版本递增、相关未使用挑战撤销和会话操作均在同一事务。错误验证码的计数在事务提交后再报错，避免被异常回滚。修改密码也递增认证版本并撤销邮箱挑战。登录签发会话校验已验证的密码哈希和认证版本，阻止使用变更前凭据的在途登录。

## 上线前真实投递验收

用户已取得 163 SMTP 授权码，凭证需直接填写在服务器；目前未发送真实邮件，也未验证阿里云服务器的实际投递。`EMAIL_SMTP_VERIFIED` 默认为 `0`；部署脚本会在停止旧服务前检查此标记和 SMTP 配置。邮件尚不可用时继续运行旧服务版本。现有服务器使用 [Workbench 分步升级说明](WORKBENCH_EMAIL_UPGRADE.md)。

1. 在 163 邮箱设置中开通 SMTP，在服务器 `deploy/.env` 填写发件邮箱、SMTP 授权码和独立 HMAC 密钥；限制配置文件权限为 `600`。升级旧安装时已有 `.env` 会被保留，需手动补齐新配置。
2. 在服务器执行 SMTP 检查。脚本不带参数只测试连接及认证；明确传入由自己控制的两个收件邮箱才会发送测试邮件。**成功连接或 SMTP 接受不等于实际收信。**
3. 人工确认 QQ、163 的收件箱/垃圾邮件收到邮件，检查延迟及发件显示名。投递失败、延迟超过验证码有效期或服务商不允许此用途时，不上线强制绑定。
4. 确认后设置 `EMAIL_SMTP_VERIFIED=1`，再按 [部署说明](../deploy/README.md) 备份、迁移和部署。上线后使用测试账号完成真实验证码注册、绑定、重置和换绑。

已安装本项目 API 依赖的服务器可执行（在 `apps/api` 目录，凭证读当前 `.env`）：

```bash
node scripts/smtp-check.cjs
node scripts/smtp-check.cjs 你控制的邮箱@qq.com 你控制的邮箱@163.com
```

仅安装 Docker 的服务器可从项目根目录运行下列临时容器。它不连接数据库，不重建或停止现有应用，也不会开启强制绑定；替换两个收件地址后再执行。所挂载脚本只读，凭证从现有 `deploy/.env` 注入，不写进命令参数。

```bash
docker run --rm --env-file deploy/.env \
  -v "$PWD/apps/api/scripts/smtp-check.cjs:/check.cjs:ro" \
  public.ecr.aws/docker/library/node:24-bookworm-slim \
  sh -c 'cd /tmp && npm install --no-save nodemailer@10.0.0 class-validator@0.14.4 dotenv@17.4.2 >/dev/null && NODE_PATH=/tmp/node_modules node /check.cjs "$@"' \
  smtp-check 你控制的邮箱@qq.com 你控制的邮箱@163.com
```

CI 的生产容器演练使用无效 SMTP 凭证且不申请验证码，通过数据库准备已验证的测试账号来检查部署和备份。它不代表真实 SMTP 验收；实际邮件流程由 mock API/E2E 套件验证。
