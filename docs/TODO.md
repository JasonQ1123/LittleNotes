## 二、P0：备份异地保存（S1）

**现状**：`deploy/backup.sh` 已做到数据库 + 头像成套备份、`pg_restore --list` 校验、SHA256 清单、失败不留半成品，但三件套**只落在同一台服务器**的 `backups/`，保留约 14 天。磁盘损坏、误删 `/opt`、`docker compose down -v` 都会导致数据全部丢失且不可恢复。

**做法**：

1. 阿里云 OSS 建同地域 bucket，RAM 子账号只授予该 bucket 的 `PutObject` / `GetObject`。
2. `backup.sh` 末尾增加上传：三件套上传后**回读校验**（对象大小与 SHA256 对比），任一步失败 `exit 1`，让 systemd 记录为失败，而不是静默通过。
3. OSS 侧生命周期保留 90 天；本地仍保留约 14 天，保持不变。
4. 每月执行一次真实恢复：从 OSS 取最新备份 → `deploy/verify-backup.sh` → 记录日期与结果。
5. 凭证只写在服务器 `deploy/.env`，不进仓库、不进部署包。

**验收**：清空本地 `backups/` 后，仅用 OSS 上的备份能恢复出可登录、记录与头像齐全的实例；上传失败时 `backup.sh` 返回非零。

## 三、P1：账号与合规

### S2 账号注销

**现状**：可以关闭、限时恢复、彻底删除**空间**，但账号本身无法注销；`README.md` 与 `ROADMAP.md` 均标注"账号注销仍待后续实现"。境内备案站点通常需要提供删除个人信息的渠道，这也是"分手后想删干净"的真实诉求。

**待确认的产品规则**（实现前先定）：

- 有共同空间时：是先要求关闭空间，还是注销时自动执行关闭流程？
- 注销后是否保留一条不含个人信息的审计记录（时间 + 用户 ID 哈希）？

**做法**：

- `POST /api/account/delete`：验证当前密码 + 二次确认；沿用改密的数据库限流，独立计数。
- 单事务内删除 `Session`、`EmailChallenge`、`EmailJob`、`PasswordChangeLimit`、`SpaceRestoreRequest`、`SpaceMembership`、`User`；**头像文件在事务提交后再删**，失败可重试。
- 前端入口放在「我们的空间 → 账号安全」，与修改密码同级，二次确认文案要明确不可恢复。
- 不删除对方账号与其记录；空间内另一方看到的昵称按既有快照规则处理。

**验收**：注销后该账号无法登录、业务数据不可恢复、头像文件被删除；对方账号与其他空间不受影响。

### S3 数据导出

**做法**：

- `GET /api/account/export` 返回 JSON：本人资料、当前空间信息、本人可见记录（含视角、约定、回访）。
- **复用 `RecordsService.view()` 的过滤逻辑**，不另写一套权限判断；私密草稿、对方未发布内容不得出现。
- 响应 `Cache-Control: no-store`，接口限流；数据量大时再考虑打包下载。
- 前端在「账号安全」提供「下载我的数据」。

**验收**：导出内容与页面可见范围完全一致；不含对方私密内容；重复导出结果稳定。

### S4 生产可观测性与告警

**现状**：全站只有 6 处 `console.*`，没有错误上报、没有健康探测、没有告警。备份失败、邮件队列卡死、清理任务异常只能靠翻 journal，用户不投诉就发现不了。

**做法**：

1. 结构化错误日志：`Errors` 过滤器输出 JSON 行（时间、method、path、status、code、requestId、耗时），按大小轮转。
2. 每日 08:00 运维汇总邮件（复用现有 163 SMTP）：备份是否成功、上次成功时间、待处理邮件任务数、清理任务结果、24 小时 5xx 数量、健康检查结果。**"没收到邮件"本身就是告警**。
3. 外部 uptime 探测 `/api/health`（该接口会查库，适合做探针），连续 3 次失败告警。
4. 可选：接入错误聚合服务，暂缓。

**验收**：手动停库 30 秒能在 2 分钟内收到告警；恢复后能确认恢复时间。

## 四、P2：工程效率

### S5 登录/注册限流持久化与测试隔离

**现状**：`AuthService.attempts` 是进程内 `Map`，默认每 IP 15 分钟 40 次。单实例可用，但重启清零、多实例不共享，与改密/邮箱限流"落库"的做法不一致。

**本地进度（2026-10-27，待合并和上线）**：登录/注册上限已支持 `AUTH_LIMIT_PER_15M`，未配置时为 40，非法配置拒绝启动；独立 E2E 进程设置为 10000，避免桌面和手机全量回归累计触发 429。数据库持久化仍未实现。

**做法**：

- 把登录/注册限流迁移到数据库（可复用 `EmailLimit` 或新增表），键为 IP 哈希，带过期清理。
- 已完成本地实现：上限改为环境变量（`AUTH_LIMIT_PER_15M`），`scripts/e2e-api.mjs` 中调高。

**验收**：重启服务后计数仍有效；`pnpm test:e2e` 连续执行两次全部通过。

### S6 ESLint 与 CI 格式检查

**进度（2026-10-20）**：格式部分已完成，根 `package.json` 提供 `format` / `format:check`，CI 在安装后执行 `pnpm format:check`；剩余 ESLint。

**做法**：`@typescript-eslint` + `eslint-plugin-vue` 推荐集，不上 `airbnb`；CI 增加 `pnpm lint`，先修到零告警再开启阻断。

### S7 依赖更新与漏洞扫描

**做法**：启用 Dependabot（pnpm + GitHub Actions，每周），CI 增加 `pnpm audit --prod`（允许已知例外清单）。当前依赖版本较新，但没有任何自动更新机制。

### S8 本地历史数据导入（时机未到）

**现状**：本地 SQLite 与生产 PostgreSQL 独立，**没有**任何"把本地记录传到线上"的通道，也刻意不提供。只有当确实存在需要保留的历史数据时才做：编写一次性迁移脚本（保留 id、时间、密码哈希），在维护窗口执行并核对行数。

## 五、P3：结构性改进

### S9 双数据库收敛

**现状**：开发用 SQLite、生产用 PostgreSQL，两套 schema 与迁移历史（`prisma/schema.prisma` 与 `prisma/postgresql/schema.prisma`），每次改模型要写两份迁移，靠 `scripts/sync-postgres.mjs --check` 兜底。

**做法**：评估开发环境直接使用 PostgreSQL（Docker），移除 SQLite 分支（`Database.atomic` 的写入队列、SQLite 迁移、schema 副本）。这会同时影响 CI、备份脚本与文档，属于大改动，等业务稳定后再评估。
